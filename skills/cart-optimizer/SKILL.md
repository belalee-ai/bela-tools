# 购物车比价助手

一句话定位：**帮普通人把一整车东西算清楚——分几单、每单勾哪几件、用哪张券、会员值不值开**，不被「凑单」反向薅羊毛。

为什么值得做（这也是向用户解释价值时的说法）：
- 同一类券每单只能用一张时，拆单有机会用上第二张。先核对账户实际有几张、各适用哪些商品，再比较拆单后的实付。
- 没勾选时，购物车给每件标的「平台加补后」是单件估价，同一张券会被好几件重复算；
- 会员有没有带来新增优惠，要和本车不用会员权益的可行方案比较；
- 平台希望你越凑越多，这个助手只在「凑单真的划算」时才建议加，否则直说不划算。

所有金额计算交给 `scripts/optimize.py`，不要心算：几十张券 × 几种拆单的组合，手算必错，而错一次用户就不再信任。你负责读图、问清楚、把结果讲成人话。

## 流程

### 1. 拿到购物车

**录屏（推荐，一段视频顶十几张截图）**：先抽关键帧再读图：

```bash
python3 <skill目录>/scripts/extract_frames.py <录屏.mp4> <输出目录>
```

它会去掉停留和慢滑的重复画面。如果关键帧仍然很多（>40 张），不要逐张读：先用 ffmpeg 拼一张缩略总览（`-vf "fps=1/4,scale=200:-2,tile=11x4"`）判断哪几段是购物车、券列表、会员页、价格明细弹窗，再只读这几段的原图。

**截图**：直接读。用户没说明的话，最有用的四类画面是：
1. 购物车列表（每件的店铺、标题、规格、数量、价格、标签）
2. 商品价格「明细」弹窗（优惠前 − 店铺优惠 − 平台优惠 − 国补 的拆分，最准）
3. 「我的权益 / 红包 / 券」页（消费券、会员券的面额、门槛、适用范围、到期时间）
4. 会员页（88VIP / PLUS 的券包）

读图时要分清这几个价格（最容易抄错）：
| 画面上的字 | 含义 | 填到哪 |
|---|---|---|
| 灰色划线价 / 优惠前 | 原价 | `list_price` |
| 官方立减 / 单品直降 | 已落实到单件的自动减价 | 从原价里扣掉，得到 `price`。需要用券的店铺满减只登记到店铺券池，避免重复扣减 |
| 平台加补后 / 券后价 / 到手价 | 可能是单件估价，也可能是当前勾选组合的分摊价。根据明细确认，不能直接假设同一张券被重复使用 | 未勾选时填 `shown_price`；勾选后用来校准 |
| 国补后 / 政府补贴 | 需要先领资格，按比例减 | `subsidy` |
| 已付定金 | 你已经付过的钱，不是优惠 | 填单件 `deposit_paid`，完整 `price` 包含已付定金；区分总成本与本次待付 |

看不清的数字标出来问，不要猜。

### 2. 整理清单，问清缺的

把识别结果整理成表（平台 / 店铺 / 商品 / 品类 / 原价 / 券前价 / 数量）给用户确认，并一次性问清：
- **这次真正要买哪些**（购物车常有上百件，只算要买的）；哪些是「想要但不急」（凑单候选）
- 手上的券：按账户、平台、店铺确认实际持有的张数、适用范围和有效期。只展示「最高可领」的券先列为待确认。库存来自同一张截图时不要重复录入。
- **会员**：确认当前会籍、账户实际开通价和专享报价。只有会员才能购买的报价须标记 `requires_membership: true`。
- **国补**：只有本人当前账户的资格、适用商品和剩余名额确认后，才把国补计入应付。仅看到商品页「补贴后约 ¥X」时，先给无补贴金额并标明待确认；同一资格在拆单或换平台后仍共用剩余名额。

满减门槛须逐张明确 `threshold_on`，不要按平台名称统一猜 list 或 running；多组叠加时填写实际 `order`。缺失门槛的券会排除并提示。

平台规则细节读 `references/taobao.md`、`references/jd.md`。规则拿不准的（例如两类消费券能不能在一单里叠加），按保守的「不能叠加」算，写进 `assumptions`，并告诉用户结算页如果显示能叠加会更省。

🔴 **计算前检查点**

- 跨平台比价先核对品牌、型号、规格、套装内容和数量。确认同款后，把各平台报价录入同一个商品的 `offers`。规格或赠品有差异时单列，按差异说明可比范围。
- 购物车里分摊了券的「到手价」只用于比较当前画面。换平台、换商品或拆单时，按已确认的券前价、券规则、会员费、补贴和运费重算。
- 缺项会影响结论时，先给能核对的画面价差或当前全选金额，并一次列出需要补的商品、券或结算明细。能按已确认条件计算时，注明估算口径。无法支撑可执行方案时，先停在核对阶段，补齐后再生成下单卡。

### 3. 计算

按 `references/input_schema.md` 写 `cart.json`，然后：

```bash
python3 <skill目录>/scripts/optimize.py cart.json --json result.json
```

脚本会：搜索最省的拆单和用券组合；对每个平台会员分别算「开 / 不开」；比较本车会员净收益；对每个凑单候选及组合重新选择会员并算增量支出；按品类汇总；查重复商品。
精确搜索覆盖报价、逐件拆分、券库存与放弃用券；成功返回时仅在已录入规则内最优。每次求解最多18件、默认30万次状态预算，可用 `search_budget` 调整预算。超过上限会明确停止，不交付未证明的“最低价”。仅在优惠库存、补贴名额、会员费等确实互不共享时才能分开计算，不能随意切车。

**核对账户和用券明细。** 录屏里的全选合计只能校验该次勾选，比较时要使用相同的账号、报价和会籍。拆分后逐单核对商品、数量、用券、国补、运费和结算预览；影响实付的条件仍未确认时，写明该条件和当前估算口径。
结果和用户结算页对不上时，先查 `stack_group`（能不能叠加）和 `threshold_on`（门槛口径），改输入重算，不要手动改结果。

### 4. 讲结论

照脚本报告的结构讲，**先结论**：
1. **一句话**：分几单、到手多少、相当于几折、比一次性全买省多少
2. **比较口径**：拆单对照保持报价、账号和会籍一致；截图估价只作参考，未核对明细不归因为重复用券。定金计入总成本，并单列本次待付。
3. **会员值不值**（必须有）：
   - 已是会员：这一车会员券帮你省了多少
   - 不是会员：核实本账户开通费和这车适用的权益后，算出净省或净亏，再给「开」或「不开」的结论。缺少这些条件时把会员判断标为待确认，已核实的非会员方案照常计算和交付。
   - 不输出通用消费额回本线。普通券替代、适用品类和拆单都会影响新增收益；已付会员费是沉没成本，不重复扣除。缺普通报价时明确告知无法确定净省。
4. **照着做**：第 1 单勾哪几件、用哪张券、应付多少；第 2 单……
5. **按品类看**：每个品类原价、到手价、几折
6. **凑单建议**：加某件只多花 ¥X（相当于几折）——只推荐用户本来就想要的；为了凑单买不需要的东西不叫省钱
7. **下单前检查**：重复加购、一次买太多的消耗品（保质期）、国补要先领资格、券的到期时间、退款金额和优惠收回规则须以平台退款页为准

最后提醒：提交前看一眼结算页「实付」，和清单差几块钱以上就截图发回来重算。

### 5. 生成可视化下单卡（必做 · 最终交付物）

**通过计算前检查点并得到可执行方案后，必须生成 HTML 下单卡**——不要只给文字结论，也不要问用户"要不要"。用户照着买的就是这张卡，文字结论只是对它的一句话补充。

用生成器一键产出（**不要手填 HTML**，金额全部来自优化器）：

```bash
python3 <skill目录>/scripts/optimize.py cart.json --json result.json
python3 <skill目录>/scripts/build_card.py result.json cart.json -o order_card.html
```

`build_card.py` 读 `optimize.py` 的输出，自动渲染四块内容（沿用 `assets/order_card_template.html` 的红发小魔女向导、勾选盖章、倒计时、进度条）：
1. **会员开/不开对比卡**：条件齐全时展示两种方案的总成本与净差。开通费或适用权益待核实时，按已核实的非会员条件生成下单卡，并在随卡说明里标注「会员待确认」。不展示通用回本线。
2. **领券清单**：自动列出这一车**实际用到**的每一张券，按会员券 / 平台券 / 店铺券 / 运费券 / 国补分组；若 `cart.json` 写了 `coupon_meta`（见下），再带上"去哪领 / 截止时间 / 小魔女一句话提醒"。领完一张勾一张。
3. **分单结算**：按计算方案的订单顺序列出平台店铺、商品、优惠、运费、包装服务费、定金和本次待付，并附可选加购组合的订单明细。只展示已知截止时间；券已过期须重新计算。
4. **付款前核对**：核对新增会员费、已计入的国补、实际使用的券和结算页实付。会员退款条件以该账户开通页为准。

`cart.json` 两个可选富化字段（没有也能跑）：
- `meta`：`title` / `subtitle` / `hero_title` / `baseline_one_order`（录屏里直接一单结算的到手价，用来对比多省多少）。
- `coupon_meta`：键是券名**子串**（如 `"满2000减300"`），值是 `{where, deadline(ISO), tag, tip, urgent}`——填了就显示"去哪领、什么时候过期、小魔女提醒"，没填则用默认文案。

模板已抽成占位符骨架，**只改样式就动 `assets/order_card_template.html`**，不要改生成器里的结构假设。

### 6. 下单留给用户

不替用户点「结算」「提交订单」或付款，也不尝试绕过平台的验证码和风控。用户的钱、用户自己点最后一下。

## 文件

- `scripts/extract_frames.py` — 录屏抽关键帧（需要 ffmpeg）
- `scripts/exact_solver.py` — 合法结算枚举与共享资源动态规划，预算不足时明确报错
- `scripts/optimize.py` — 算账器（搜索最省拆单 + 用券组合；对每个会员算开/不开；比较增量收益）
- `scripts/build_card.py` — **下单卡生成器**：读 `optimize.py --json` 输出，渲染单文件 HTML（会员对比 + 领券清单 + 分单结算 + 核对），这是最终交付物
- `assets/order_card_template.html` — 下单卡模板骨架（红发小魔女向导 + 勾选盖章 + 倒计时 + 进度条，已抽成 `{{占位符}}`，改样式只动这里）
- `references/input_schema.md` — cart.json 字段，写输入前读
- `references/taobao.md` — 淘宝/天猫：消费券、88VIP、国补、价格口径
- `references/jd.md` — 京东：PLUS、品类券、国补
- `examples/taobao_10items_2026.json` — 2026 年购物车录屏整理的历史输入。未确认的国补不计入本次估算，注明有效期的券按运行时间判断。

## 修复验证

运行 `python3 -m unittest discover -s <skill目录>/tests -v`。用例为合成购物车，覆盖优惠资格、全局分配、数量拆单、运费、补贴上限、定金、会员与加购联动，以及独立穷举对照。历史录屏样例不是当前活动的已验证报价。
